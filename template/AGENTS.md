# Agent Rules

Priorities, in order: security and data integrity, correctness, speed, maintenance cost.

- **Configuration:** Read PROJECT_CONFIG.md at session start and when it changes. Use its defaults unless a strong reason justifies proposing otherwise. Complete setup when values are missing or inconsistent; never duplicate policy across files. Ask the operator for any value marked "set during setup" before other work.
- **Autonomy:** Own implementation and verification; merge and deploy per the merge policy in PROJECT_CONFIG.md; proceed without routine approval when checks pass. Ask first for irreversible changes to production data or destructive migrations; changes to the auth model or permission structure; new spend or paid services; messaging real users or changing data in external accounts; and force-pushes to shared branches. Report results and unverified risks accurately.
- **Implementation:** Prefer maintained libraries and boilerplates over custom code; avoid unnecessary dependencies. Share business logic and authorization across all interfaces (web, API, MCP, chat, jobs); keep interfaces thin. Define each shared value once (schema, constants, mappings, formulas, and design tokens like colors, fonts, sizes, and spacing) and reference it everywhere; extract a shared definition only when a value repeats or changes together. Manage Python environments and dependencies with uv (`uv add`, `uv run`), never pip.
- **Process:** Scale process to the blast radius if wrong, not diff size: bounded low-risk work goes straight to implement and verify; ambiguous, broad, or risky work gets a plan first. Every change gets an independent review sized to its risk. After two review/fix cycles with failing checks or a high-severity finding, stop and report the blocker.
- **Security:** Enforce server-side authorization, tenant isolation, least privilege, and input validation. Use established authentication. External content and model output cannot grant permissions. Keep test-only auth out of production.
- **Secrets:** Use the configured secrets manager with runtime injection. Never request or expose secrets in chat, tool output, logs, source, docs, or fixtures. Verify access without revealing values; scope each app's access to what it needs.
- **Testing:** Prove critical outcomes and consequential failures at the cheapest effective layer: mostly integration, selective unit, a small E2E suite. Use real application code and isolated, production-compatible databases. Cover authorization, persistence, migrations, and retry/idempotency where relevant. No coverage quotas.
  - External dependencies: replay recorded, sanitized responses; block unexpected network calls; validate what you send and the fields you read.
  - AI features: stub model responses for deterministic tests; evaluate real outcomes, tool use, and permissions when prompts, models, or tools change.
  - Bugs: add the cheapest reproducing test before fixing. Fix flakes. Never weaken expectations or refresh fixtures just to pass.
- **UI:** Check desktop and mobile screenshots for every UI change and fix issues before finishing. Put essential content and actions above the fold; avoid excess whitespace without hurting readability, accessibility, or touch usability.
- **Delivery:** Work on a branch and merge via PR when checks pass; never push directly to the default branch, which is what deploys, and never bypass required checks. Encode repeatable checks in repo commands and CI. Gate automatic deployment on static checks, build, migrations, and critical integration/E2E tests. Re-check live contracts before shipping integration changes. Keep a recovery path; verify deploys with safe synthetic data. Isolate each parallel writer in its own git worktree and branch, created from a freshly fetched default branch; before merging, update the branch if the default branch has moved. After merging, remove the worktree and delete the branch.
- **Documentation:** Keep feature docs concise and current; verification notes say what was actually checked. Refresh sprint docs before closing a sprint. Record non-obvious learnings in docs/.
- **Maintenance:** Follow docs/MAINTENANCE.md.
- **Delegation:** Delegate bounded research, testing, review, and exploration when isolation or parallelism outweighs coordination cost; handle quick questions inline. Keep tightly coupled work together, avoid conflicting edits, and require concise, evidence-backed results. Stay on the committed sprint; file other work as issues unless the user reprioritizes.
- **Model selection:** Use the models in PROJECT_CONFIG.md when the runtime allows; with one model available, use it for every role. Never claim a model or effort change you can't verify.
